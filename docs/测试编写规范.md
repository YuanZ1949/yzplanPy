## 二、逐条根因与规则

### 问题 1: 测试模块顶层直接赋值 `QT_QPA_PLATFORM` 劫持整个会话

**现象**

本地测试全绿，CI 全红。CI 上出现渲染差异和随机崩溃。

**根因**

`tests/test_qpa_titlebar_render.py:24` 写了：

```python
os.environ["QT_QPA_PLATFORM"] = "windows"
```

这是直接赋值，不是 `setdefault`。83 个测试文件中，49 个用 `setdefault`，33 个完全不设 `QT_QPA_PLATFORM`：

```python
os.environ.setdefault("QT_QPA_PLATFORM", "offscreen")
```

**机制**

pytest 在 collection 阶段**先导入全部测试模块**再跑测试。Qt 在 `QApplication` 构造时读取 `QT_QPA_PLATFORM` 环境变量，之后修改无效。由于只有 `test_qpa_titlebar_render.py` 用直接赋值，无论导入顺序如何，它都会覆盖 `setdefault` 的结果。整个会话跑在 windows 平台。CI runner 无头显示器，渲染差异导致测试失败。

**佐证**

该文件 docstring 第 9 行自述「要求独立进程：QT_QPA_PLATFORM=windows 必须在首个 Qt 初始化前设置」。作者知道要独立进程但没落实隔离。文件第 18 行还有导入顺序依赖的 hack：

```python
if QApplication.instance() is not None:
    pytest.skip("qpa 像素测试需独立进程（本进程已存在 offscreen QApplication）",
                allow_module_level=True)
```

这依赖于 offscreen 的 QApplication 先被创建，本身就是脆弱的导入顺序假设。

**规则**

`QT_QPA_PLATFORM` 只允许用 `os.environ.setdefault("QT_QPA_PLATFORM", "offscreen")`。禁止直接赋值。需要真实窗口平台的测试必须独立进程运行，并从主套件 `--ignore`。

**正例**

```python
import os
os.environ.setdefault("QT_QPA_PLATFORM", "offscreen")

# CI workflow 中用 --ignore 隔离需要真实平台的测试文件：
# python -m pytest --ignore=tests/test_qpa_titlebar_render.py ...
```

**反例**

```python
import os
os.environ["QT_QPA_PLATFORM"] = "windows"  # 直接赋值，劫持整个会话
```

### 问题 2: 测试模块顶层创建 QApplication

**现象**

有 20 个测试文件在模块顶层创建 QApplication（AST 精确统计，不含函数 / fixture 内部）。不同文件用不同写法：

```python
# 写法 1
app = QtWidgets.QApplication.instance()
if app is None:
    app = QtWidgets.QApplication(sys.argv)

# 写法 2
_qapp = QtWidgets.QApplication.instance() or QtWidgets.QApplication(sys.argv)

# 写法 3
app = QApplication.instance() or QApplication([])
```

**根因**

顶层副作用。**首个被导入的模块决定全局 QApplication 的平台与属性**，而导入顺序由文件名字典序隐式决定。这使测试行为依赖文件命名，不可控。

**规则**

QApplication 只在 `tests/conftest.py` 的 session-scoped fixture 创建，测试文件通过参数注入获取。禁止模块顶层 `QApplication(...)` 或 `QApplication.instance() or QApplication(...)`。

**注意：这是迁移项。** 20 个文件不要求一次性改完。但**新增文件必须用 fixture**，现有文件逐步迁移。

**正例**

```python
# conftest.py
@pytest.fixture(scope="session")
def qapp():
    app = QtWidgets.QApplication.instance()
    if app is None:
        app = QtWidgets.QApplication(sys.argv)
    return app

# test_xxx.py
def test_something(qapp):
    widget = SomeWidget()
    ...
```

**反例**

```python
# test_xxx.py  (模块顶层)
import sys
from PySide6.QtWidgets import QApplication
app = QApplication.instance() or QApplication(sys.argv)  # 顶层副作用
```

### 问题 3: fixture 全局扫荡式清理 widget

**事故**

`tests/test_rss_icon_cache.py` 曾有一个 `_icon_cache_cleanup` fixture 遍历 `QApplication.allWidgets()`，对 `_RssPageWidget` 实例做 `close()` + `deleteLater()` + `processEvents()` + `sendPostedEvents()`。

**根因**

创建这些 widget 的集成测试 `test_sidebar_reload_uses_cache` 已在提交 `97f33b0` 被删除。清理循环成为**死代码**，而它主动操作全局 widget 树，触发潜在 Qt 堆损坏（退出码 `0xC0000374` STATUS_HEAP_CORRUPTION）。修复提交 `77e95ad` 把 fixture 简化为只清 `sidebar_data._ICON_CACHE`。

**现行代码**（`tests/test_rss_icon_cache.py:58-62`）：

```python
@pytest.fixture(autouse=True)
def _icon_cache_cleanup():
    sidebar_data._ICON_CACHE.clear()
    yield
    sidebar_data._ICON_CACHE.clear()
```

**规则**

fixture 只清理自己创建的对象。禁止遍历 `QApplication.allWidgets()` 做类型过滤清理。

**正例**

```python
@pytest.fixture
def my_widget(qapp):
    w = MyWidget()
    yield w
    w.close()  # 只清理自己创建的
```

**反例**

```python
@pytest.fixture(autouse=True)
def cleanup():
    yield
    for w in QApplication.allWidgets():
        if isinstance(w, MyWidget):
            w.close()
            w.deleteLater()
    QApplication.processEvents()
```

### 问题 4: 依赖真实桌面的测试未守卫

**事故**

`tests/test_screenshot_mcp.py` 用 `win32gui.CreateWindowEx` 创建真实 Win32 窗口并用 GDI 截图，断言像素熵（非黑像素占比 > 0.5）。`tests/test_screenshot_module_hotkey.py` 注册真实全局热键。CI runner 在 session 0 运行，无交互式桌面 → 窗口渲染为黑/失败。修复提交 `1a6fc1d`。

**根因**

CI 的 Windows Server 2022 runner 运行在 session 0，没有交互式桌面。创建的窗口无法正常渲染。

**规则**

需要交互式桌面的测试必须加守卫：

```python
@pytest.mark.skipif(bool(os.environ.get("CI")), reason="requires interactive desktop session")
```

**关键陷阱（必须记住）**

裸 `os.environ.get("CI")` 会导致**测试报错而不是跳过**。原因：pytest 的 `MarkDecorator` 在**装饰期**求值 marker 参数并存原始值。GitHub Actions 下 `CI=true` → 存字符串 `"true"`，随后 `_pytest/skipping.py` 的 `evaluate_condition` 对字符串条件当作**源码 `eval()`** → `NameError: name 'true' is not defined`。

本地 `CI` 未设置时返回 `None` → 正常工作。所以本地验证发现不了。

**必须包 `bool()`**：`bool(os.environ.get("CI"))` 返回 `True` 或 `False`，`eval()` 看到的是布尔字面量，不会报错。

**正例**

```python
@pytest.mark.skipif(bool(os.environ.get("CI")), reason="requires interactive desktop session")
def test_real_window_rendering():
    hwnd = win32gui.CreateWindowEx(...)
    ...
```

**反例**

```python
@pytest.mark.skipif(os.environ.get("CI"), reason="requires interactive desktop session")  # 缺 bool()
def test_real_window_rendering():
    # CI 上 pytest 报 NameError: name 'true' is not defined，测试 ERROR 而非 SKIP
    ...
```

### 问题 5: 跨盘符 `os.path.relpath` 抛 ValueError

**事故**

`scripts/audit_styles.py` 的 `audit_file()` 调 `os.path.relpath(path, REPO)`。CI 工作区在 `D:`，pytest `tmp_path` 在 `C:` → `ValueError: path is on mount 'C:', start on mount 'D:'` → 17 个测试失败（`test_style_audit.py`、`test_style_audit_exempt.py`）。修复提交 `6848e70`。

**性质**

预先存在。`git log -- scripts/audit_styles.py` 最后一次改动是 `e0524b6`，非本批次。CI 在 base 提交 `d73418c` 也失败。

**为什么本地发现不了**

本地仓库与临时目录同在 `C:` 盘。

**现行修复代码**（`scripts/audit_styles.py:121-128`）：

```python
def audit_file(path):
    try:
        rel = os.path.relpath(path, REPO).replace("\\", "/")
    except ValueError:
        # 跨盘符（CI 上仓库在 D:、pytest tmp_path 在 C:）时 relpath 抛 ValueError；
        # 退化为绝对路径（正斜杠），保证审计继续而非崩溃。
        rel = os.path.abspath(path).replace("\\", "/")
```

**回归测试**（`tests/test_style_audit.py:51-62`）：

```python
def test_audit_file_cross_drive_path_does_not_crash(tmp_path, monkeypatch):
    import scripts.audit_styles as audit_styles
    monkeypatch.setattr(audit_styles, "REPO", "Z:\\nonexistent\\repo")
    f = _audit_text(tmp_path, 'b.setStyleSheet("QPushButton { background: #ff0000; }")\n')
    hits = audit_styles.audit_file(str(f))
    assert any(h["rule"] == "hex_color" for h in hits), hits
```

**规则**

禁止假设仓库与临时目录同盘。涉及路径计算时必须处理 `ValueError`。用 monkeypatch 改 REPO 到别的盘符来模拟 CI，不要依赖本机布局。

**正例**

```python
try:
    rel = os.path.relpath(path, BASE).replace("\\", "/")
except ValueError:
    rel = os.path.abspath(path).replace("\\", "/")
```

```python
# 回归测试：用 monkeypatch 模拟跨盘
def test_cross_drive(monkeypatch):
    monkeypatch.setattr(module, "REPO", "Z:\\nonexistent")
    ...
```

**反例**

```python
# 假设同盘，CI 上崩溃
rel = os.path.relpath(path, REPO)
```

### 问题 6: 生产资源未隔离

**事故**（2026-09-08）

`tests/test_todo_notes_ui.py` 直接跑在生产库 `data/app.db` 上，清空用户 12 条真实便签（后从 WAL checkpoint 恢复）。

**根因**

`tests/conftest.py` 当时无任何 DB 隔离。测试用例直接操作生产数据库。

**现行修复**（`tests/conftest.py:48-64`）：

```python
@pytest.fixture(autouse=True)
def _isolate_db(monkeypatch, tmp_path):
    """所有测试默认使用临时数据库，绝不触碰生产 data/app.db。"""
    db = tmp_path / "test.db"
    import modules.todo_store as todo_store
    import modules.blog.store as blog_store
    monkeypatch.setattr(todo_store, "DB_PATH", str(db))
    monkeypatch.setattr(blog_store, "DB_PATH", str(db))
    todo_store._get_conn().close()
    blog_store._get_conn().close()
    return db
```

**规则**

任何持久化资源（DB/文件/注册表/配置）必须重定向到 `tmp_path`。**新增 store 时必须同步加入 `_isolate_db`。**

**正例**

```python
# 新增 store 后，在 conftest.py 的 _isolate_db 中追加：
import modules.new_store as new_store
monkeypatch.setattr(new_store, "DB_PATH", str(db))
new_store._get_conn().close()
```

**反例**

```python
# 新增 store，忘记加入 _isolate_db → 测试直接操作生产 DB
import modules.new_store as new_store
# ...测试用例直接读写 new_store 的表
```

### 问题 7: monkeypatch 泄漏

**事故**（commit `#e8e8e8`）

`core.theme.base.resolve_dark` 与 `core.theme.resolve_dark` 的双绑定 patch 未还原，泄漏到同进程后续测试。浅色主题下取到暗色板（#e8e8e8）。

**现行设施**（`tests/conftest.py:20-45`）：

`_force_dark()` / `_restore_dark()` 辅助函数，docstring 记录了该事故。调用方必须在 try/finally 或 fixture teardown 中成对使用。

**规则**

优先用 pytest `monkeypatch` fixture（自动还原）。必须手工 patch 模块全局时，成对 restore，放在 try/finally 或 fixture teardown。

**正例**

```python
# 优先：用 monkeypatch，自动还原
def test_theme(monkeypatch):
    monkeypatch.setattr(core.theme.base, "resolve_dark", lambda mode: True)
    ...

# 必须手工 patch 时：成对还原
def test_theme():
    orig = core.theme.base.resolve_dark
    core.theme.base.resolve_dark = lambda mode: True
    try:
        ...
    finally:
        core.theme.base.resolve_dark = orig
```

**反例**

```python
def test_theme():
    core.theme.base.resolve_dark = lambda mode: True
    # 忘记还原 → 泄漏到后续测试
    ...
```

### 问题 8: 单进程全量套件不稳定 → 分块运行

**现象**

全量套件单进程运行**非确定性**崩溃。观测崩溃点约在 144、167、575、580 个测试处，退出码 `0xC0000374`（堆损坏）或 `0xC0000005`（访问违例）。

**性质**

预先存在。CI 在 base 提交 `d73418c` 也失败。

**现行方案**

CI 拆成 4 块独立 pytest 进程（`.github/workflows/python-app.yml`），每块独立运行、独立生成 junitxml。

**已有隔离范式**

`tests/test_todo_notes_ui.py` 用父子进程隔离保护 0xC0000005 崩溃路径（第 15-31 行）：

```python
# 主套件收集到 _child 时一律 skip
_SUBPROCESS_CHILD = pytest.mark.skipif(
    "os.environ.get('_YZ_SUBPROCESS_CHILD') != '1'",
    reason="仅在子进程隔离中运行（0xC0000005 崩溃保护）；主套件跳过",
)
```

父用例（第 593-613 行）用 `subprocess.run` 启动子 pytest：

```python
def test_inline_edit_content_refresh_no_crash_subprocess():
    result = subprocess.run(
        [sys.executable, "-m", "pytest",
         f"tests/test_todo_notes_ui.py::{child_name}",
         "-q"],
        timeout=30,
        capture_output=True,
        env={**os.environ, "_YZ_SUBPROCESS_CHILD": "1"},
        cwd=str(Path(__file__).resolve().parent.parent),
    )
    assert result.returncode == 0
```

子用例（第 616-629 行）用 `@_SUBPROCESS_CHILD` 装饰，只在子进程里运行。

**规则**

不要假设单进程全量套件稳定。会触发已知崩溃路径（0xC0000005、0xC0000374）的测试用父子进程隔离。

### 问题 9: CI 可诊断性差 + 新增文件不被 CI 运行

**事实**

GitHub 自 2024 起移除匿名日志访问（API 403），CI 失败详情只能通过 check-runs annotations 读取。现行设施（`.github/workflows/python-app.yml`）：

- 每块 `--junitxml=chunkN.xml`
- `actions/upload-artifact@v4` 上传 `pytest-results`
- `::error::` / `::warning::` 注解上报步骤（第 63-97 行）

**重要陷阱**

workflow 的 4 个 chunk 是**显式枚举测试文件名**，不是自动发现。例如 chunk 1 列出了 `tests/test_about_tab.py tests/test_adaptive_table.py ...` 这样的完整列表。**新增测试文件如果不加进 chunk 列表，CI 根本不会运行它。**

**规则**

新增测试文件必须加入对应 chunk 列表。本地复现不了的 CI 问题先加注解诊断。

## 三、写测试的检查清单

新增或修改测试文件时，逐条过一遍：

1. **顶层无副作用？** 不写环境变量（除 `setdefault`）、不建 QApplication、不读写文件/DB。
2. **`QT_QPA_PLATFORM` 只用 `setdefault`？** 禁止 `os.environ["QT_QPA_PLATFORM"] = ...` 直接赋值。
3. **QApplication 来自 conftest 的 session fixture？** 新增文件禁止模块顶层创建 QApplication。
4. **fixture 只清理自己创建的对象？** 没有 `allWidgets()` 扫荡。
5. **需要交互式桌面？** 加 `bool(os.environ.get("CI"))` 守卫。注意必须包 `bool()`。
6. **涉及路径计算？** 跨盘符安全，处理 `ValueError`。
7. **涉及持久化资源？** 重定向 `tmp_path`，新增 store 同步加入 `_isolate_db`。
8. **手工 patch 全局？** 成对还原或用 `monkeypatch`。
9. **会触发已知崩溃路径（0xC0000005）？** 父子进程隔离。
10. **新增测试文件已加入 CI chunk 列表？** 检查 `.github/workflows/python-app.yml`。
11. **本地验证：** `python scripts/audit_styles.py --check`（期望 0 violations）+ 相关测试通过。

## 四、pytest / Qt 陷阱速查

| 陷阱 | 表现 | 根因 | 解法 |
|------|------|------|------|
| `QT_QPA_PLATFORM` 赋值 vs setdefault | CI 上整个会话跑错平台 | 赋值覆盖 setdefault | 只用 `setdefault` |
| 模块顶层 QApplication | 首个导入决定全局 app 属性 | 导入顺序隐式决定 | conftest session fixture |
| `allWidgets()` 扫荡清理 | 堆损坏 0xC0000374 | 操作不属于自己的对象 | fixture 只清理自己的 |
| 裸 `os.environ.get("CI")` skipif | 测试 ERROR 而非 SKIP | pytest eval() 把字符串当源码 | 包 `bool()` |
| `os.path.relpath` 跨盘符 | ValueError 崩溃 | Windows 不支持跨盘符 relpath | try/except ValueError |
| monkeypatch 双绑定泄漏 | 浅色取暗色板 | 两层 import 绑定不同对象 | 双 patch + 双 restore |
| 崩溃路径单进程跑 | 非确定性 0xC0000005 | Qt 事件循环残留累积 | 父子进程隔离 |
| pytest.ini 注释提到的先例 | `smoke_test.py` 被排除出收集 | 顶层副作用（全局 app 字体、对生产 DB 启动完整 app） | `python_files = test_*.py` |

**本地环境备注：** 仓库在 `C:`；必须用 `.venv\Scripts\python.exe`（系统 python/Anaconda 在 import PySide6 时崩溃，`icuuc.dll`，`0xc0000139`）。

**CI 环境：** `windows-latest`（Windows Server 2022）、Python 3.11.9、`QT_QPA_PLATFORM: offscreen`、工作区在 `D:`。

## 五、CI 约束

1. **测试分块运行。** CI 把测试拆成 4 块独立 pytest 进程，每块独立生成 junitxml。不要假设单进程全量套件稳定。

2. **新增文件必须加入 chunk 列表。** workflow 的 4 个 chunk 是显式枚举文件名（`.github/workflows/python-app.yml`），不是自动发现。新增 `tests/test_xxx.py` 后必须把它加进某个 chunk 的文件列表，否则 CI 不会运行。

3. **诊断设施。** 每块输出 `--junitxml=chunkN.xml`，失败通过 `::error::` 注解上报。GitHub Actions 不提供匿名日志，只能通过 check-runs annotations 读取详情。

4. **隔离标记。** `conftest.py` 注册了 `qpa` marker（`config.addinivalue_line("markers", "qpa: ...")`），用于标记需要窗口会话的 QPA 测试。
